\author{Chandra Irugalbandara}

\begin{abstract}
Coding agents now build and operate much of the software they touch, mostly from a terminal. We propose CLI-first development: a capability is done only when it works from the product's command-line interface, and that CLI is the reference client against which the other clients are checked. In a personal-finance product that adopted the rule, coverage fell behind until a dedicated phase restored it, and an agent's pass through the CLI found a safety control that held only on the web path. We then test a popular claim, that CLIs cost agents less than Model Context Protocol (MCP) servers, in 704 runs that hold the product fixed and vary the protocol, the agent's knowledge of the interface, and whether it may compose operations. What the agent knew mattered more than the protocol: agents that learned the CLI from its help cost 1.6 to 2 times as much as agents given the curated MCP server. With a compact command sheet, the CLI matched the server on chains of dependent steps for the stronger model and, composed, cost 36 to 39\% less on two tasks that repeat an operation, at the price of coarser oversight. Follow-ups (1{,}440 runs) found that which parts of the sheet mattered depended on the model, and that on the product's rewritten version the composed CLI cost less than its MCP server, partly because that server had grown.
\end{abstract}

\section{Introduction}

Agents are becoming a large share of the users of developer tools. Cloudflare reports that agents accounted for a quarter of the use of its command-line tool in March 2026, up from single digits a year earlier, and for 48\% by late September~\cite{cloudflare2026cf}. Inside product teams the shift shows in version control: in \sysA{}, the personal-finance product we study, 75\% of commits carry a coding agent's co-authorship trailer. Those agents need to run the software they change, not just compile it.

We propose \emph{CLI-first development}, a process with two rules: a capability is done only when it works from the product's command-line interface (CLI), and the CLI is the \emph{reference client} that the product's other clients, including the web application and any Model Context Protocol (MCP) server, are checked against. The proposal makes two claims. One concerns process: a CLI held to these rules lets the agents that build a product exercise and verify all of it. We examine it in \sysA{}'s version history. The other concerns cost and is widely argued, while the few measurements disagree: that a CLI is cheaper for agents than an MCP server because MCP loads every tool definition into the model's context~\cite{schmitt2026circleci,qi2026ibm}, or more expensive because every call starts a process~\cite{mindstudio2026mcpcli}.

To test the cost claim we held one product fixed and varied only the interface its agents used (Figure~\ref{fig:teaser}), crossing three factors: the \emph{protocol} (MCP tool calls or shell commands), what the agent \emph{knows} about the interface before it starts, and whether it may \emph{compose} operations into one program. If the interface did not matter, every configuration would cost what \sysA{}'s curated MCP server costs, and every ratio we report would be 1. What the agent knew moved cost more than the protocol did. On chains, giving a CLI agent a command sheet instead of help lowered its cost relative to the MCP server from 1.6--2.0 to 0.9--1.2, a wider swing than the gap between the best CLI configuration and the server. Our thesis follows: the case for CLI-first rests on the agents that build and check a product, and for agents in general, what they are told about an interface matters more than which protocol carries it. We report five findings from the main experiment and two from follow-ups:

\begin{itemize}
\item \finding{F1.} An agent that learned the CLI from its help cost 1.6 to 2 times as much as an agent given the curated MCP server's schemas (Section~\ref{sec:f1}).
\item \finding{F2.} For the same operations, an MCP server generated from the CLI cost 1.3 to 1.8 times as much as the curated one; it also returned larger results, so the effect of catalogue size alone is not isolated (Section~\ref{sec:f2}).
\item \finding{F3.} On chains of dependent steps, the CLI with a 1.1k-token command sheet and composition could not be told apart from the curated server for the stronger model, Sonnet, and cost 1.2 times as much for the weaker, Haiku (Section~\ref{sec:f3}).
\item \finding{F4.} On two tasks that repeat an operation, the same configuration cost 36--39\% less than the curated server for both models; Haiku saved only on bulk entry, and where one write was needed there was no consistent advantage (Section~\ref{sec:f4}).
\item \finding{F5.} Composition moved the unit a person could review from single actions to whole scripts, and agents on both protocols, in four of eight configurations, reported success they had not achieved (Section~\ref{sec:f5}).
\item \finding{F6.} Which parts of the command sheet mattered depended on the model: without its options the weaker model cost 1.24 times as much on chains and without its output shapes 1.10 times; the stronger model needed only the output shapes (1.19). A sheet four times larger cost no more under a warm shared cache but 1.27 to 1.59 times as much with a cold one (Section~\ref{sec:f6}).
\item \finding{F7.} On the product as rewritten since, the composed CLI with a sheet cost 0.60 to 0.90 times as much as the product's MCP server on chains and 0.32 to 0.48 times on repetition tasks. Part of that came from the server doubling its catalogue: against its original 24 tools, the composed CLI was level for the weaker model on chains and cheaper elsewhere. Addressing accounts by code instead of id made no detectable difference (Sections~\ref{sec:f7} and~\ref{sec:isolation}).
\end{itemize}

\noindent The paper contributes (1) a definition of CLI-first development (Section~\ref{sec:principle}); (2) a single-product case study of the rule in practice (Section~\ref{sec:cases}); (3) a caching-aware cost model that separates what an interface costs an agent into description, discovery and composition (Section~\ref{sec:mcp}); (4) an exploratory experiment and three follow-up waves, 2{,}144 runs in all, with every run, transcript and analysis released (Sections~\ref{sec:experiment} and~\ref{sec:followup}); and (5) principles for agent-ready CLIs and controls for agents that act through them (Sections~\ref{sec:principles}--\ref{sec:guardrails}).

\section{Related Work}
\label{sec:related}

\paragraph{Delegation and oversight}
The debate between direct manipulation and delegation to agents is older than large language models~\cite{shneiderman1997direct,maes1994agents}. Norman warned that delegation works only when people keep an accurate sense of what the agent is doing and can take control back~\cite{norman1994agents}, and Horvitz's mixed-initiative principles~\cite{horvitz1999principles} and Amershi et al.'s guidelines for human-AI interaction~\cite{amershi2019guidelines} turn that concern into design advice. Work on automation describes how oversight degrades: the operator of a highly automated system is left with the hardest decisions and the least practice at them~\cite{bainbridge1983ironies}, the right level of automation differs by stage of a task~\cite{parasuraman2000model}, and trust has to be calibrated to reliability~\cite{lee2004trust}. An agent narrows the person's gulf of execution and can widen their gulf of evaluation~\cite{hutchins1985direct}, and stating intent is itself hard for non-experts~\cite{nielsen2023paradigm,zamfirescu2023johnny}. F5 bears on both gulfs.

\paragraph{Agent-computer interfaces and tool use}
SWE-agent showed that interface design changes agent performance: a purpose-built interface resolved 18.0\% of SWE-bench Lite tasks~\cite{jimenez2024swebench} against 11.0\% for a plain shell~\cite{yang2024sweagent}. CodeAct found that acting through executable code outperformed JSON and text tool calls by up to 20\% in success rate across 17 models~\cite{wang2024codeact}, and InterCode and Terminal-Bench evaluate agents in shells~\cite{yang2023intercode,merrill2026terminalbench}. Documentation alone lets models use unfamiliar tools about as well as demonstrations do~\cite{hsieh2023tooldoc}, and ReWOO and LLMCompiler cut model invocations by planning tool calls ahead~\cite{xu2023rewoo,kim2023llmcompiler}. Translating language into shell commands is a long-studied problem~\cite{lin2018nl2bash}.

\paragraph{GUI, API, CLI and MCP agents}
GUI agents beat CLI agents on 440 desktop tasks until the CLI's missing capabilities were filled in~\cite{zhou2026guicli}, and take 2.7 to 4.3 times more steps than necessary~\cite{abhyankar2025osworldhuman}; API-first and hybrid agents are faster~\cite{lu2024axis,zhang2025apigui,zhang2025ufo2}, and MCP tools raise computer-use agents' success~\cite{jia2025osworldmcp}. Comparisons of MCP and CLIs disagree. Across seven scaffoldings, paired MCP-to-CLI cost ratios ranged from 0.43 to 29~\cite{alier2026scaffolding}; in 120 runs MCP was 23\% faster and 2.5\% cheaper than an equivalent CLI~\cite{zechner2025mcpcli}. Holding a backend fixed, Smithery's 756 runs against public APIs found native MCP ahead of a CLI with descriptions on GitHub's REST API in success (91.7\% against 83.3\%), median tokens (28.8k against 82.9k) and time (10.4 against 24.9~s)~\cite{mao2026smithery,nordicapis2026mcpcli}, and Scale Labs' 50 long-horizon tasks found the CLI's advantage depended on model and task and mattered little for frontier models~\cite{hou2026scale}.

\paragraph{Practice and lineage}
``Agent experience'' has become a design concern~\cite{biilmann2025ax,baer2026agentsfirst}, and products increasingly give the UI and the agent one set of actions~\cite{builderio2026app,posthog2026golden}. For CLI input, named flags beat single JSON payloads on accuracy and cost~\cite{mastykarz2026dont,poehnelt2026rewrite}, and Mistral gives every interactive prompt a flag~\cite{mistral2026spaces}. The architecture underneath CLI-first is old: composable programs~\cite{mcilroy1978unix}, ports and adapters~\cite{cockburn2005hexagonal}, command-line design guidance~\cite{clig2020} and API usability research~\cite{myers2016api}; the decay of a shared interface is a form of architecture erosion~\cite{perry1992foundations,desilva2012erosion}. CLI-first differs from API-first in naming which client must work first and giving it the role of reference.

\paragraph{How this study differs}
The two fixed-backend studies are closest to ours. We differ in three ways: (1) we vary what the agent knows about the interface and whether it may compose as separate factors, so their effects can be told apart; (2) we decompose cost by token type under prompt caching and model it, rather than reporting totals; and (3) we score a production product's database state rather than an agent's answer.

\section{CLI-First Development}
\label{sec:principle}

A team practises CLI-first development when it holds two rules. First, a capability is complete only when it can be exercised from the product's CLI; other clients may ship it at the same time or later, but not instead. Second, the CLI is the reference client: when the web application, the MCP server or an embedded assistant disagrees with the CLI about what the product does, the disagreement is a defect in one of them, and checks written against the CLI define the expected behaviour. The first rule without the second produces coverage that can drift; the second without the first produces a reference for part of the product.

Three kinds of agent interact with such a product (Figure~\ref{fig:arch}). Coding agents and operators' agents run in a shell and are the CLI's main users: they exercise features without a browser, configure deployments and check their own changes. Embedded agents call the same core operations and get no more power than any other client. Users' agents, the assistants that end users delegate to, usually run where no shell exists and reach \sysA{} through an MCP server with OAuth-scoped access. CLI-first serves them indirectly, by making every capability a scriptable operation that any protocol can expose; it does not guarantee that they will: \sysA{}'s open-source core has 125 CLI commands but 24 MCP tools.

The analogy with mobile-first~\cite{wroblewski2009mobile,wroblewski2011mobile} holds for the order of work and fails on constraint: mobile-first started from the most limited client, CLI-first from the most capable, and its new user is an agent acting for a person. Accessibility is a closer precedent: the interfaces that expose an application to a screen reader stay complete only where teams treat gaps as defects.

\section{A CLI-First Product}
\label{sec:cases}

\paragraph{Method}
We studied \sysA{}, a personal finance and tax product for Sri Lanka whose agent guidance adopts the CLI-first rule and which the author develops. The design is a single-case study with the author as participant-observer, in the tradition of autobiographical design~\cite{neustaedter2012autobiographical} and following case-study guidance from software engineering~\cite{runeson2009case}. The data are the product's git history (417 commits), architecture documents and commit messages at a fixed snapshot (13 September 2026). For CLI coverage we counted CLI commands and API route handlers, excluding authentication, at a series of dates; the ratio of counts is a proxy for parity, not a mapping of commands to routes. For agent involvement we counted commits whose message contains a \texttt{Co-Authored-By: Claude} trailer. The case can show what happened in one product; it cannot show how often CLI-first works elsewhere. Commit messages were themselves written with agent assistance and may be more explicit, and more favourable, than an independent record~\cite{bird2009git}.

\subsection{Coverage fell behind under a written rule and recovered in a dedicated phase}
\sysA{} combines a double-entry ledger, a versioned tax engine and AI agents that explain a user's financial position. Its domain core has no input/output or framework imports, and its CLI and HTTP API build their services through one composition function. The project's agent guidance states the order of work: ``Core + CLI first --- all domain logic runs from the terminal before any HTTP server exists,'' then the API, then web and mobile clients. 311 of its 417 commits carry an agent trailer.

\finding{The rule did not hold on its own.} An HTTP API with 19 feature routes existed from the first day, and over four weeks the API grew while the CLI did not: by 14 July the CLI had 13 commands against 54 feature routes, a ratio of 0.24 (Figure~\ref{fig:parity}). The roadmap then inserted a ``CLI completion'' phase ahead of new domain work, and within two days the ratio reached 0.82. Five domains built immediately afterwards each received core logic, API routes and a CLI command group within about twelve minutes, in one agent session. Coverage then fell to 0.73 as the API gained routes the CLI did not; the open-source core now runs a continuous-integration check that fails when a route has neither a command nor a recorded reason for lacking one. We have no data yet on whether the check holds coverage.

\subsection{A pass through the CLI found a control that held on only one path}
\finding{Once the CLI covered the product, a coding agent's pass through it found defects in the core.} One agent-assisted commit (\texttt{862ed06}, 19 July) records the defects ``found during a full CLI end-to-end pass''. The CLI had never set up the checkpointer that the HTTP server configures for the embedded agents, so the agents' history commands crashed and the human-approval gate on their write tools silently did nothing when invoked from the CLI. Data export crashed for any user who had computed their tax, and a command that posts imported transactions misreported how many it had posted. The approval-gate defect could not be seen from the web client, which reached the agents through the HTTP server that set the checkpointer up. That gate had been fixed for the web path a month earlier; the CLI pass found that the same guarantee did not hold on another path into the core. These observations, from one product and one participant-observer, motivate study S2 in Section~\ref{sec:agenda}.

\section{What an Interface Costs an Agent}
\label{sec:mcp}

An MCP server publishes typed tools whose definitions the agent's host loads into the model's context~\cite{mcp2024spec}; the model calls tools one response at a time, possibly several in parallel. With a CLI that emits structured output, an agent can instead write a chain of operations once as a program and run it as one tool call, so that intermediate data move through pipes or files rather than through the model, as in Figure~\ref{fig:teaser}.

\paragraph{A cost model}
Consider $k$ operations, each needing the result of the one before. Let $S$ be the fixed prompt prefix (system prompt and interface description), $u$ the user's request, $a_i$ and $r_i$ the tokens of the $i$-th call and its result, $c$ the tokens of a pipeline script and $f$ its filtered output. With direct calls there are $k+1$ model passes, and pass $j$ reads $P_j = S + u + \sum_{i<j}(a_i + r_i)$. Without caching, the input tokens processed are
\begin{equation}
I_{\text{calls}} = (k+1)(S+u) + \sum_{i=1}^{k}(k+1-i)(a_i+r_i),
\label{eq:calls}
\end{equation}
quadratic in $k$ when results are of similar size, while a single pipeline needs two passes:
\begin{equation}
I_{\text{pipe}} = 2(S+u) + c + f.
\label{eq:pipe}
\end{equation}
With prompt caching, cache writes cost $\omega$ times the base input rate and cache reads $\rho$ times; for one provider $\rho = 0.1$, $\omega$ is 1.25 for five-minute and 2 for one-hour entries, and output costs five times the input rate~\cite{anthropic2026caching}. Direct calls then cost approximately $\omega P_1 + \rho\sum_{j\le k}P_j + \omega\sum_i(a_i+r_i)$ input-token equivalents and the pipeline $\omega(S+u+c+f)+\rho(S+u)$ (Table~\ref{tab:cost}). Caching removes most of the quadratic term but not the $k+1$ sequential passes, nor the cost of every intermediate result entering the context once. When many agents share a prefix, even the first pass may read $S$ from the cache.

\paragraph{Discovery and repetition}
Two further terms decide whether a pipeline is available. The first is \emph{discovery}. Equation~\ref{eq:pipe} assumes an agent that knows the commands and the shape of their output. An MCP server supplies that knowledge in $S$; an agent that must learn a CLI reads help instead, taking $d$ extra passes that add $h$ tokens, written to the cache once and re-read on every later pass. Whether this exceeds the CLI's saving in $S$ depends on $d$, $h$ and the passes that follow. The second is \emph{repetition}. For $n$ independent operations of one kind, direct calls can run in parallel within one pass, but the model writes all $n$ calls and all $n$ results enter the context. A loop over a CLI command avoids the per-call overhead; its length is constant in $n$ when it iterates over the product's own data, as in Figure~\ref{fig:teaser}, and grows with $n$ when the arguments must be written out.

\paragraph{Research questions}
\label{sec:hypotheses}
The model raises four questions. We formed the predictions after the first wave of the experiment (Section~\ref{sec:history}) and test them on data that include that wave, so they are exploratory.
\begin{description}
\item[RQ1, knowledge.] Does an agent that must learn a CLI from its help cost more than one given an MCP server's schemas? \emph{Predicted: yes.}
\item[RQ2, description size.] For the same operations, does an MCP server generated from the CLI cost more than a curated one? \emph{Predicted: yes.}
\item[RQ3, composition.] When the agent knows the commands, does a composed CLI cost less than the curated MCP server on chains of dependent operations, and on tasks that repeat an operation? \emph{Predicted: yes, more so for repetition.}
\item[RQ4, oversight.] What does composition do to what a person can review? \emph{No prediction.}
\end{description}

\noindent Composition's economics come from code as the agent's action space, not from the shell; MCP tools can also be called from code in a sandbox~\cite{anthropic2025codeexec,anthropic2025advancedtools,cloudflare2025codemode}, though standard MCP clients do not offer it. A CLI brings composition with the interface, along with costs: scripts must anticipate output shapes that MCP declares, chains can fail halfway, shell quoting is fragile~\cite{mastykarz2026dont}, every invocation starts a process, and a shell carries ambient authority. A pipeline planned before reading data keeps untrusted content out of the control flow~\cite{debenedetti2025camel}; one that interpolates data into commands, like Figure~\ref{fig:teaser}'s loop, does not.

\section{An Exploratory Experiment}
\label{sec:experiment}

\subsection{Design}
We held one product, its data and its tasks fixed and varied the interface. The product was \sysA{}'s open-source core at commit \texttt{0277747}, whose CLI (125 commands, 120 with \flag{json}) and MCP server (24 tools) call the same services and database. A \emph{configuration} fixes three factors (Table~\ref{tab:arms}). The \emph{protocol} is MCP tool calls or shell commands. \emph{Knowledge} is what the interface description tells the agent before it starts. MCP configurations receive tool schemas. CLI configurations receive one of four descriptions: help alone; the core's agent skill, pasted into the prompt (646 tokens naming command groups and rules, but no options); the core's five skills, installed for the agent to load if it chooses; or a \emph{command sheet} generated from the CLI's own definitions (1{,}134 tokens giving usage, options and JSON output shape for the 14 commands that do what \cfg{MCP-24}'s tools do). \emph{Composition} is whether the agent may combine commands: one-per-call configurations permitted only the \cmd{salli} executable, while composed ones asked the agent to compose dependent steps and allowed pipes, \cmd{jq}, scripts and (from wave 4) Python. \cfg{MCP-24} is the core's own, curated server, whose results are compact summaries. \cfg{MCP-102} is generated from the CLI, with one tool for each of 102 of the 120 commands that support \flag{json} (administrative command groups are left out), and returns the CLI's JSON, so it differs from \cfg{MCP-24} in both catalogue size and result size.

\finding{What the experiment can and cannot show.} It compares these configurations on one product, six tasks and two models from one provider. It cannot say how often CLIs beat MCP servers in general, and it does not test the process claim of Section~\ref{sec:cases}.

\paragraph{Tasks and scoring}
Six tasks could all be completed with the operations available to \cfg{MCP-24}. Four are \emph{chains} of $k = 1, 2, 4$ and $8$ operations, with nominal dependency depths 1, 2, 4 and 6: report the tax owed; record a cash expense; record a salary, compute the tax and set a reminder carrying the figure; and create an account, post to it, find the expense account with the largest balance, refund it, and set a reminder carrying the tax and the bank balance. Two are \emph{repetition tasks}: record 25 expenses listed in the request (bulk entry), and set a reminder for every expense account over LKR~20{,}000 (fan-out, Figure~\ref{fig:teaser}). Each ran on a small ledger (16 accounts, 30 entries) and a large one (106 accounts, 440 entries); fan-out needs one write on the small ledger and 24 on the large, which makes the small cell a control where composition has nothing to compose. A \emph{cell} is one task on one ledger, so there are 12 cells and 24 combinations of model and cell. Every run used a freshly seeded user. The one-operation tax question was scored from the answer and the other tasks against the database, by the expected records; the two-step and repetition tasks also required that no other records of the same kind exist on the task's dates, while the 4- and 8-step checks did not look for extra records.

\paragraph{Interface asymmetries}
\cfg{MCP-24}'s reminder tool takes free text, while the CLI's \cmd{reminders add} takes it as a \texttt{KIND} argument that neither the skill nor the sheet explains. The CLI accepts account codes. The core's documentation, our prompt for the CLI configurations and the command sheet's header all said identifiers could be shortened to a unique prefix, which \cmd{entry add} did not accept. On the small ledger the 8-step task's target account is necessarily the one created in its first step.

\paragraph{Harness}
The agent was Claude Code 2.1.293 in headless mode driving Claude Haiku~5.5 and Claude Sonnet~5.5. Its system prompt was replaced by a short task prompt common to all configurations plus a configuration-specific paragraph; user settings were excluded, MCP tool search disabled, and only the configuration's tools enabled. The composed configurations' paragraph alone gave a reason to compose, so ``that intermediate output does not have to pass through you''; no other configuration was told anything about efficiency. The common prompt also said that the request was the user's confirmation for any change it asked for, so no configuration paused for approval. \cfg{MCP-24} ran the core's server over stdio with its OAuth user lookup replaced by the seeded user. Composed configurations ran with permissions bypassed under a deny-list of deletion, network, version-control and package-manager commands, and with a directory holding only \cmd{salli} prepended to the path; there was no sandbox, and the environment held the test instance's database URL and service keys. No transcript shows a command that bypassed the CLI. Caching used one-hour entries shared across runs: in 702 of 704 runs the first call read the prompt and interface description from a cache warmed by earlier runs.

\subsection{Collection history}
\label{sec:history}
\finding{The design grew in five waves, each started after the previous one's results were visible} (Table~\ref{tab:waves}). The first wave, a pilot on the chain tasks, found the CLI more expensive than \cfg{MCP-24}; the command-sheet configurations, the repetition tasks and the research questions came afterwards, and the pilot's 128 \cfg{MCP-24} and \cfg{CLI skill/step} runs are part of the analysed data. Of 947 runs attempted, 243 were superseded and 704 retained; the run ledger lists each with its wave, parallelism, permissions and fate. Four harness problems caused the supersessions. Claude Code's allowlist matcher refused composed commands containing variables, quoting or loops (in 29 of 128 wave-1 composed runs, all of which still succeeded), so composed configurations were re-collected without it (128 runs). A deny-list that also blocked interpreters was in force for 32 repetition-task runs, three of which had a script refused; all 32 were re-collected. The composed chain runs we kept used that deny-list, and none invoked an interpreter. Parallel runs shared a temporary directory and overwrote each other's files, so the 80 composed runs that had used a shared path, and one that ran beside a smoke test, were collected again one at a time; because this rule selected runs by behaviour, Section~\ref{sec:robust} restores them. One run was stopped by the operator in error and one produced no output; both were collected again.

\subsection{Measures and analysis}
\label{sec:analysis}
For each run we recorded success; cost; tokens of each kind, summed over the run's agent invocations; passes, tool calls and characters of tool output; and time as reported by the agent harness, summed over invocations. Cost is at list prices: \$0.10, 0.20, 0.01 and 0.50 per million uncached input, cache-write, cache-read and output tokens for Haiku, and \$2, 4, 0.20 and 10 for Sonnet. These prices reproduce the harness's reported cost for every run. The outcome is cost relative to \cfg{MCP-24}: in each cell the ratio of geometric-mean costs, combined over cells by the geometric mean. We report two targets of inference. \emph{For these tasks}, the 95\% interval is a Welch-type $t$ interval for the mean log ratio over cells, with runs within cells as the sampling unit and Satterthwaite degrees of freedom; $p$-values come from a stratified permutation test (10{,}000 permutations), Holm-adjusted over 24 comparisons~\cite{holm1979}. A bootstrap over runs within cells~\cite{efron1994bootstrap} gives similar intervals and is in the released data. \emph{For tasks like these}, a $t$ interval over tasks uses each task's log ratio averaged over its two ledgers; with four chain tasks it is wide, and with two repetition tasks uninformative. We compare models as a ratio of ratios, overall and per task, and give absolute differences in cents.

\subsection{F1. Agents that learned the CLI from its help paid 1.6 to 2 times as much}
\label{sec:f1}
\finding{An agent that had to learn the CLI from its help cost more than an agent given \cfg{MCP-24}'s schemas} (RQ1). On chains \cfg{CLI help/comp} cost 1.99 times as much with Haiku and 1.62 times with Sonnet, about 0.2 and 1.7 cents more per task, with intervals above 1 for these tasks and for tasks like these; it cost more in all 8 cells for Haiku and 7 of 8 for Sonnet. These agents made two to four help calls per run, and at $k=8$ took a median of 15.5 passes against 7 for \cfg{MCP-24} (Haiku). A skill that named the command groups but no options did not close the gap (1.22 to 2.08).

\subsection{F2. The generated MCP server cost more than the curated one in every cell}
\label{sec:f2}
\finding{\cfg{MCP-102} cost more than \cfg{MCP-24} in all 12 cells for both models} (RQ2): 1.79 and 1.57 times as much on chains with Haiku and Sonnet, and 1.53 and 1.34 times on repetition tasks ($p = 0.002$ throughout). Its schemas took 9.7k tokens against 3.0k, and it also returned 2.3 to 3.4 times as many characters of results, so the comparison does not isolate catalogue size. Against the CLI it was generated from, used with the command sheet and composed, it was the more expensive interface on both models and both task families.

\subsection{F3. On chains, the CLI with the command sheet could not be told apart from MCP for Sonnet, and cost more for Haiku}
\label{sec:f3}
\finding{With the command sheet and composition, Sonnet's agents cost about what \cfg{MCP-24}'s did on chains, and Haiku's cost more} (RQ3). Sonnet's ratio was 0.89 (95\% CI 0.78--1.02; Holm $p = 0.26$), under a cent less per task; over tasks like these the interval, 0.57--1.39, is too wide to claim either parity or a saving. Haiku's ratio was 1.21 (1.11--1.31; Holm $p = 0.002$), about 0.07 cents more per task. The models differed: Sonnet's ratio was 0.74 times Haiku's (0.67--0.82). At $k=8$ on the large ledger Sonnet composed its work into three tool calls and four passes, and Haiku composed its work into ten calls and nine passes.

\finding{Result size is a third factor.} The CLI's JSON is fuller than \cfg{MCP-24}'s summaries. With one command per call, \cfg{CLI sheet/step} agents received about twice as many characters of results as \cfg{MCP-24}'s (1.98 times for Haiku, 1.96 for Sonnet) and cost 1.28 and 1.24 times as much, although, like \cfg{MCP-24}'s agents, they issued one operation per call. Composed agents could filter results before they reached the model, and received 1.64 and 1.07 times as many characters.

\subsection{F4. Composition paid when an operation repeated}
\label{sec:f4}
\finding{On the two repetition tasks, the composed CLI with the command sheet cost 36--39\% less than \cfg{MCP-24}} (RQ3): 0.64 with Haiku (95\% CI 0.56--0.73; Holm $p = 0.005$), about 0.3 cents less per task, and 0.61 with Sonnet (0.50--0.74; $p = 0.002$), about 4 cents less. Cost fell in three of four cells for Haiku and four of four for Sonnet. \finding{The saving was not spread alike.} Haiku saved on bulk entry only (0.41; fan-out 1.02), while Sonnet saved on both (0.67 and 0.56). Sonnet's ratio was 1.65 times Haiku's on bulk entry and 0.55 times on fan-out, so the overall ratio of ratios, 0.95, hides an interaction between model and task. In the control cell, the fan-out that needs one write, composition had nothing to compose and gave no consistent advantage: \cfg{MCP-24} was cheaper for Haiku (0.11 against 0.18 cents) and more expensive for Sonnet (1.83 against 1.61). Two tasks cannot establish generality; the interval over tasks spans 0.20 to 1.91 for Sonnet.

Composition without the sheet had similar point estimates that were not established (\cfg{CLI skill/comp}, 0.79 for Haiku and 0.64 for Sonnet; Holm $p = 0.19$ and $0.067$), and restoring the superseded runs moves Sonnet's to 0.81. One command per call reversed the effect for Sonnet, at 2.90 times \cfg{MCP-24}. On bulk entry its agents issued the 25 writes in parallel, with account identifiers shortened to a prefix as the documentation, our prompt and the command sheet said they could be; \cmd{entry add} rejected each with a traceback, the agents repeated the writes, and the two bulk cells cost 5.7 and 6.6 times \cfg{MCP-24}.

\subsection{F5. Composition coarsened oversight, and neither protocol made reports reliable}
\label{sec:f5}
\finding{The configuration that saved most put 25 writes behind one tool call} (RQ4). With \cfg{MCP-24} or one command per call, each tool call carried at most one write; on the bulk task the composed agents placed a median of 25 writes in a single call. No person approved anything in the experiment, so this describes what a reviewer would be shown, not how reviewers would fare: per-action approval would become approval of a script. In 31 of the 96 composed repetition runs the script also sent the writes' output to \texttt{/dev/null}, so not even the transcript records what each write returned. \finding{Five of the 11 failures ended in a report of success}, 5 of 704 runs, as coded by the author. Two were with \cfg{MCP-24} (an omitted account; the wrong one of two similar names), one each with \cfg{MCP-102} and \cfg{CLI sheet/step} (each refunded the wrong account), and one with \cfg{CLI skill/comp} (reminder texts carrying stray quotation marks). One \cfg{MCP-24} agent ended: ``Created 23 reminders \dots{} for the expense accounts over LKR 20,000'', when 24 qualified. The other six failures disclosed what had gone wrong.

\subsection{F6. Which parts of the sheet mattered depended on the model}
\label{sec:f6}
\finding{Design.} We derived four variants from the command sheet used above, each keeping the sheet's header: one without the JSON output shapes (608 tokens); one without the options (915); one with names and one-line descriptions only, which removes both (389); and one with the full sheet plus usage and options for 97 more commands, 111 of the CLI's 125 (4{,}620 tokens; commands nested two levels deep were left out). The first three form a two-by-two design, options by output shapes, which we analyse as main effects. Each variant ran composed, on the paper's commit, tasks and ledgers, five times per cell with Haiku and three times with Sonnet. \cfg{MCP-24} and the full sheet ran again in the same wave as references (576 runs, of which 572 succeeded). The wave reproduced the main experiment. Against \cfg{MCP-24}, the full sheet cost 1.19 and 0.90 times as much on chains for Haiku and Sonnet (previously 1.21 and 0.89), and 0.57 and 0.59 times on repetition tasks (previously 0.64 and 0.61). Each configuration's absolute cost was within 10\% of its value in the main experiment.

\finding{For Haiku both the options and the output shapes lowered cost on chains; for Sonnet only the output shapes did} (Table~\ref{tab:ablation}). Averaged over the other element, removing the options cost Haiku 1.24 times as much on chains (1.17--1.32; Holm $p<0.001$ over the eight main effects) and removing the output shapes 1.10 times as much (1.03--1.17; $p=0.02$). Without options, Haiku's agents read help, a median of one call against none, and took more passes. For Sonnet, removing the output shapes cost 1.19 times as much (1.05--1.34; $p=0.046$), and removing the options made no detectable difference (0.92, 0.81--1.03). On repetition tasks, where composition did the work, neither element had a detectable effect for either model. Sonnet's comparisons are noisier than Haiku's: at this commit 5 to 9 of its 36 runs per sheet, the reference included, hit tracebacks from the identifier-prefix defect.

\finding{Whether the sheet's size mattered depended on the cache.} Under the warm shared cache, the four-times-larger sheet cost about what the full sheet did (0.96 and 1.00 for Haiku, 0.95 and 1.30 for Sonnet; none detectable). Re-priced as if each run had written its own cache, it cost 1.27 to 1.59 times as much: its 3{,}500 extra tokens are written once per conversation at the cache-write rate, as the cost model predicts (Section~\ref{sec:mcp}). Size matters wherever the prefix is not shared, and the experiment's warm cache hides that. For the same reason the ablation does not settle F2. By the cost model, re-reading \cfg{MCP-102}'s larger catalogue accounts for a median of 16\% to 53\% of its extra cost, depending on model and task family (chains or repetition tasks), so its catalogue and its larger results both contributed.

\finding{The output shapes also kept writes on the record.} Without them, the composed agents more often sent their writes' output to \texttt{/dev/null}. This happened in 17 of 32 repetition runs without output shapes and 19 of 32 with names only, against 4 of 32 with the full sheet and 7 of 32 without options. An agent that does not know what a write returns is more likely to discard it, which leaves a reviewer less to check.

\subsection{F7. On the rewritten product, the composed CLI with a sheet cost less than MCP}
\label{sec:f7}
\finding{Design.} \sysA{}'s developer, the author, rewrote its core after the main experiment and finished the rewrite after this paper's first version, so the rewrite cannot be treated as independent of the study. At commit \texttt{1322f84} the CLI is a TypeScript client of the HTTP API. It names accounts by code or name as well as by id, adds filters such as \flag{type} and \flag{balances}, accepts the identifier prefixes its documentation promises, and reports errors without tracebacks. The MCP server, which we call \cfg{MCP-46}, grew from 24 to 46 tools, with 6{,}599 tokens of definitions, and still takes account ids only. We ported the harness, keeping the prompts, tasks, ledgers and checks. Each run's CLI was authenticated by a personal access token that was revoked afterwards. Scripted right and wrong solutions of every task through both protocols confirmed that the checks still tell them apart (48 cases); that the tasks are equally hard on both versions is not established. The command sheet and the agent skill were regenerated from the new CLI by the same rules. The sheet covers 33 commands in 3{,}010 tokens, so each configuration name in Table~\ref{tab:rewrite} denotes a regenerated description. Five configurations ran five times per cell with Haiku and three times with Sonnet (480 runs, of which 475 succeeded).

\finding{With the sheet and composition, the CLI now cost less than \cfg{MCP-46} for both models on these tasks} (Table~\ref{tab:rewrite}). On chains it cost 0.90 (0.84--0.96) times as much for Haiku and 0.60 (0.49--0.74) for Sonnet, cheaper in 6 and 8 of 8 cells; on repetition tasks, 0.48 and 0.32 times. Relative to the main experiment these ratios changed by factors of 0.74 (0.67--0.82) and 0.67 (0.54--0.84) on chains and 0.76 and 0.52 on repetition tasks. Re-running the paper's commit in the ablation wave changed the same ratios by factors of only 0.89 to 1.01, every interval containing 1. Over tasks like these, the chain interval excludes 1 for Sonnet (0.53--0.68) but not for Haiku (0.76--1.06). The result holds when each run writes its own cache (0.81 and 0.67 on chains). A CLI learned from help still cost Haiku twice as much on chains under the warm cache (2.00, 1.91--2.09), unchanged from the main experiment. Re-priced with a cold cache, it cost 1.10 times as much for Haiku and 0.78 times for Sonnet, because \cfg{MCP-46}'s larger catalogue is expensive to write.

\finding{Several differences between the versions line up with the change.} Each of the following is consistent with it, and the next subsection tests the first two.
\begin{itemize}
\item \emph{The MCP server became more expensive.} Its absolute cost rose by 0 to 15\%. That accounts for about half of Haiku's change on chains and up to a third of the others.
\item \emph{Only the CLI gained code and name addressing.} On the bulk task, the CLI's one-call-per-write agents passed the request's account codes in 800 of 800 writes, while \cfg{MCP-46}'s agents looked up ids and passed them in 800 of 800.
\item \emph{The CLI's errors no longer carry tracebacks.} None appeared in any of 384 CLI runs, against 48 of 512 before. With one command per call, Sonnet's repetition ratio fell from 2.90 to 0.73.
\item \emph{The composed agents received less text than \cfg{MCP-46}'s,} 0.21 to 0.88 times as many characters against 0.78 to 1.64 before. This was not because the CLI's records became compact: an unfiltered account list is still 1.9 times as long per account as MCP's (226 against 121 characters; 2.3 times at \texttt{0277747}). The agents asked for less, using the new filters and \texttt{jq}.
\end{itemize}

\finding{The regenerated descriptions had flaws of their own.} The sheet documents \cmd{accounts list}'s output as a list, but with \flag{balances} the command returns an object of accounts and balances. A \texttt{jq} error followed in 11 of the 14 Haiku sheet runs that used the flag. The generator recorded one output shape per command and missed that a flag changes it. The regenerated skill tells agents to confirm before they write, against the harness's rule that the request is the user's confirmation. In two runs Haiku asked for a go-ahead before computing tax, and failed.

\subsection{What the isolating runs show}
\label{sec:isolation}
\finding{Design.} A third wave tested the first two of those differences directly. It ran alone on the machine, four runs at a time (384 runs, all of which succeeded). \cfg{MCP-24} as rewritten is \cfg{MCP-46} serving only the 24 tools of the paper's \cfg{MCP-24}, with \texttt{1322f84}'s schemas (3{,}122 tokens of definitions). It emulates a CLI that addresses accounts as MCP does. \cfg{MCP-46} and the CLI with the sheet ran again as references and reproduced the rewrite wave: the ratio between them changed by factors of 0.93 to 1.17, every interval containing 1.

Which of the remaining differences produced that change is not identified: the filters, the absent tracebacks or the regenerated sheet. The sheet's mis-documented flag recurred: a \texttt{jq} error followed in 21 of the 24 Haiku runs that used \flag{balances}.


\subsection{Oversight and the harness in the follow-ups}
\label{sec:followup-oversight}
\finding{Of the follow-ups' nine failures, three were silent false successes.} Two agents refunded the wrong account and reported the refund done, one through \cfg{MCP-24} and one through the CLI. Another created 22 of 24 reminders and reported one for each qualifying account. Both wrong refunds followed a trial balance that lists balances by account id alone: the agents joined 106 bare identifiers to the account list in their reasoning, named the wrong account, and reported success. Two failures were the consent requests above and four were disclosed; the isolation wave had none.

\finding{The harness gave the agents more than they needed.} The composed configurations ran with permissions bypassed under a deny-list and without a sandbox. Until the isolation wave, the agents' environment also held the test server's database address and service keys, which the TypeScript CLI does not need. No agent read the environment. Agents used \texttt{/tmp} directly instead of their own temporary directory in 83 of the 1{,}440 follow-up runs. In 10 runs they found the files in which Claude Code saves large outputs with a wildcard spanning every project on the machine. In the main experiment the same pattern picked up another session's output in two runs, whose transcripts we redacted; the follow-ups' transcripts show no such leak. One agent wrote into the home directory. In four runs agents listed the machine's processes. In the isolation wave, two Sonnet agents checking whether their writes had finished saw other concurrent runs' command lines this way, including another run's prompt and data. Neither acted on them, but runs on one machine were not isolated from one another. None of this harmed the runs, but it is the ambient authority that control C5 addresses. The access tokens were not scoped either: at \texttt{1322f84} a personal access token acts with the user's full rights.

\section{Controls for Agents That Act Through a CLI}
\label{sec:guardrails}

An agent with a shell, a person's credentials and access to untrusted content is exposed to indirect prompt injection~\cite{greshake2023indirect,debenedetti2024agentdojo}; with network access it has all three elements of Willison's lethal trifecta: private data, untrusted content and a way to send data out~\cite{willison2025trifecta}. A coding agent that reads content generated from users' documents while holding an operator's credentials fits this description, and OWASP names the risk excessive agency~\cite{owasp2025agency}. Rules therefore have to be enforced in the core. We propose five controls and report which ones \sysA{} has.

\paragraph{C1, approval out of band}
A destructive or irreversible command should create a pending action on the server and return its identifier; the action runs only after a person approves it on a separate channel. A \flag{yes} flag the agent can pass is not consent. F5 makes this pressing: approval should attach to a script's effects, not its text. \sysA{} implements it only for return preparation, and its approval gate for the embedded agents once failed open on the CLI path (Section~\ref{sec:cases}).

\paragraph{C2, agent identities with least privilege}
Agents should hold short-lived, scoped, read-only-by-default credentials distinct from the person's. \sysA{} scopes external agents through OAuth for MCP. At \texttt{0277747} its CLI did not authenticate at all, acting as whichever user its local configuration named; at \texttt{1322f84} it authenticates with personal access tokens, but they carry no scopes and act with the user's full rights. Credentials in environment variables or arguments are visible to child processes and transcripts.

\paragraph{C3, deterministic computation where correctness matters}
Figures people act on should come from code, with the model explaining them, as in \sysA{}'s rule that the model never computes money or tax.

\paragraph{C4, attributable audit}
Every action should be logged with the acting agent and the person it acted for. At both commits \sysA{} logs MCP tools' actions but not those of the CLI, which at \texttt{1322f84} reaches the core through an API that does not audit them, so the surface we recommend for agents is the one that is not audited.

\paragraph{C5, containment below the shell}
Agents that run CLIs should do so in sandboxes with restricted file-system and network access, using signed, pinned releases. Command allowlists sit at the wrong level for composition: the harness's matcher refused composed calls in 29 of 128 runs, and our own harness, which then bypassed permissions under a deny-list without a sandbox, is an example of what teams do instead. Its agents used \texttt{/tmp}, read the harness's session files and listed processes (\S\ref{sec:followup-oversight}). Composed scripts add partial failure without rollback, retries without idempotency keys, and data interpolated into commands, so writes should be idempotent and every rule enforced in the core.

\section{Discussion}
\label{sec:discussion}

\paragraph{What CLI-first does and does not buy}
The experiment does not support the claim that a CLI is the cheaper way for any agent to use a product (Table~\ref{tab:findings}). A curated MCP server was cheaper than a CLI the agent had to learn, and faster. Its agents met no tracebacks, truncated outputs or stalled commands, and each of its actions could be reviewed on its own. Since users' agents reach \sysA{} through MCP, nothing here argues for moving them. What the evidence supports is narrower: a CLI with a compact command sheet cost about as much as the curated server on chains for Sonnet, less on two repetition tasks, and less than a server generated from the same commands. On the product as rewritten since, the composed CLI with a sheet cost less than its MCP server on these tasks for both models, partly because the server had doubled its catalogue; against the server's original 24 tools it was level for the weaker model on chains and cheaper elsewhere (F7). The process claim, that a complete CLI lets coding agents build and verify the product, rests on the case and is the subject of study S2 in the agenda below.

\paragraph{Description is a design object}
The largest effects came from what the agent was told, not from the protocol. On chains, the command sheet did more than composition; a skill that taught rules without options did little; and skills loaded on demand cost more than a description supplied up front. On repetition tasks, composition did most of the work. For MCP, the curated server's advantage over the generated one points the same way, though that comparison also varies result size. The ablation narrows this: which parts of a sheet a model needed depended on the model, and its size mattered where the prefix was not shared (F6). Both suggest treating the interface description as something to design and measure. The newest models may need less of it~\cite{hou2026scale}.

\paragraph{What MCP can do instead}
Several of the CLI's advantages here are not specific to a shell. Code execution with MCP presents a server's tools as a code API, so an agent can compose calls and filter data before it reaches the model~\cite{anthropic2025codeexec,cloudflare2025codemode}. Programmatic tool calling does the same within the model API, and tool search loads tool definitions on demand rather than up front~\cite{anthropic2025advancedtools}, which addresses the cost of a large catalogue that is not cached (F2, F6). Tool use examples show usage that a schema cannot express, the role the sheet's options and output shapes played in F6. Advice on writing tools recommends concise response formats, filtering, and names rather than opaque identifiers~\cite{anthropic2025writingtools}, as P3 does. None of these was tested here; a confirmatory study should include them.

\paragraph{Delegation, oversight and access}
Composition trades the granularity of oversight for cost, and on both protocols agents sometimes reported success they had not achieved, in the follow-ups as in the main experiment. A sheet without output shapes also made composed agents discard what their writes returned more often (F6). A CLI is not itself accessible to people~\cite{sampath2021accessibility}, though people who delegate do not use it. Whether delegation through agents improves access, and how people review composed actions, is the subject of study S4.

\paragraph{Limits}
We did not measure the cost of maintaining coverage. CLI checks cannot see layout, rendering or client-side state, and checks that put a language model in the loop are no more deterministic than the browser tests they replace.

\section{Conclusion}
We have argued that a product's capabilities should first become usable from its command line, and that this CLI should be the reference client against which its other clients are checked. In one product, coverage fell behind until a dedicated phase restored it, and a pass through the CLI found an approval gate that worked on only one path into the core. Holding the product fixed, we found that a CLI is not cheaper for agents because it is a CLI. Cost depended mostly on what the agent knew. Composition paid when an operation repeated, and in the main experiment the curated MCP server was fastest and easier to review. Follow-ups showed that which parts of a sheet an agent needs depends on the model. On the rewritten product, the composed CLI with a sheet cost less than its MCP server, partly because the server had grown and not because the CLI accepted account codes. For a CLI-first product, the description an agent receives, a command sheet for the CLI and a curated catalogue for MCP, is part of the interface and should be designed and measured like the rest of it.
